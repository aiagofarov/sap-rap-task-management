# SAP RAP Task Management

A task management API implemented using the **SAP ABAP RESTful Application Programming Model (RAP)** in SAP BTP ABAP Environment.

The application uses a **managed RAP business object**, CDS views, behavior definitions, EML, and an OData V4 service.

## Architecture

```text
OData V4 Client
       |
       v
Service Binding (ZUI_TASKDEMO_O4)
       |
       v
Service Definition (ZUI_TASKDEMO)
       |
       v
Projection View (ZC_TASKDEMO)
Projection Behavior Definition
       |
       v
Interface View (ZI_TASKDEMO)
Base Behavior Definition
       |
       v
Behavior Pool (ZBP_I_TASKDEMO)
       |
       v
Database Table (ZTASKDEMO)
```

The managed RAP framework handles standard CRUD operations and persistence. Custom logic is implemented in the behavior pool.

### Repository Objects

All objects belong to package `ZRAP_TASKS`.

| Object | Type | Description |
|---|---|---|
| `ZTASKDEMO` | Database Table | Persistent task data |
| `ZI_TASKDEMO` | CDS View | Root interface entity |
| `ZI_TASKDEMO` | Behavior Definition | Managed behavior, field mapping, determinations, validations, and actions |
| `ZBP_I_TASKDEMO` | Behavior Pool | Business logic implementation |
| `ZC_TASKDEMO` | CDS View | Projection entity |
| `ZC_TASKDEMO` | Behavior Definition | Exposes CRUD operations and the custom action |
| `ZUI_TASKDEMO` | Service Definition | Exposes `ZC_TASKDEMO` as `Tasks` |
| `ZUI_TASKDEMO_O4` | Service Binding | OData V4 endpoint |

## Data Model

The persistent table `ZTASKDEMO` contains:

| Field | Type | Description |
|---|---|---|
| `client` | CLNT | Client key |
| `task_id` | SYSUUID_X16 | Task UUID, primary key |
| `title` | CHAR(100) | Task title |
| `status` | CHAR(10) | Task status |
| `created_at` | UTCLONG | Creation timestamp |

The CDS interface view `ZI_TASKDEMO` exposes the fields as `TaskId`, `Title`, `Status`, and `CreatedAt`.

The RAP behavior definition uses:

- **Managed numbering** for `TaskId`.
- **Read-only `CreatedAt`** populated by a determination.
- Standard `create`, `update`, and `delete` operations.
- Field mapping between the CDS entity and database table.

## Business Logic

### Determination: `setCreatedAt`

Triggered when a task is created:

```abap
determination setCreatedAt on modify { create; }
```

The implementation updates `CreatedAt` using EML in local mode:

```abap
MODIFY ENTITIES OF ZI_TASKDEMO IN LOCAL MODE
  ENTITY Task
  UPDATE FIELDS ( CreatedAt )
  WITH VALUE #(
    FOR key IN keys
    (
      %tky      = key-%tky
      CreatedAt = utclong_current( )
    )
  )
  FAILED DATA(lt_failed)
  REPORTED DATA(lt_reported).
```

The timestamp is assigned automatically during RAP transactional processing.

### Validation: `validateTitle`

Triggered during the save phase:

```abap
validation validateTitle on save { create; update; }
```

The validation reads the task title using EML.

If `Title` is empty, the implementation:

- Adds the task to `failed-task`.
- Adds a message to `reported-task`.
- Marks the `Title` field using `%element-Title`.
- Rejects the save operation.

Error message:

```text
Task title cannot be empty
```

### Action: `completeTask`

Defined in the base behavior definition and exposed through the projection:

```abap
action completeTask result [1] $self;
```

The action implements the following state transition:

```text
OPEN ──completeTask──> DONE
```

Processing steps:

1. Read the current `Status` using EML.
2. Reject tasks whose status is not `OPEN`.
3. Update valid tasks to `DONE` using `MODIFY ENTITIES`.
4. Read the updated entities.
5. Return the updated task through the action result.

If the task is not `OPEN`, the action adds an entry to `FAILED` and reports:

```text
Only OPEN tasks can be completed
```

Nested EML operations use separate `FAILED` and `REPORTED` response variables. Their contents are then propagated to the action's response parameters.

This ensures that unsuccessful action requests return an appropriate OData error rather than an empty result.

## OData V4 API

The service definition exposes:

```abap
expose ZC_TASKDEMO as Tasks;
```

The OData V4 service is published through `ZUI_TASKDEMO_O4`.

`<SERVICE_ROOT>` below refers to the service URL generated by the service binding.

### Create a Task

```http
POST <SERVICE_ROOT>/Tasks
Content-Type: application/json
```

```json
{
  "Title": "Prepare technical interview",
  "Status": "OPEN"
}
```

**Response:** `201 Created`

RAP generates `TaskId`, and the determination sets `CreatedAt`.

### Read Tasks

```http
GET <SERVICE_ROOT>/Tasks
```

**Response:** Collection of task entities.

### Update and Delete

Standard update and delete operations are enabled in both the base and projection behavior definitions.

### Complete a Task

`completeTask` is exposed as an OData V4 bound action.

The action is invoked for a specific task using the action URL defined in the service metadata.

For a task with `Status = OPEN`, the action changes its status to `DONE` and returns the updated entity.

### Validation Error

Creating or updating a task with an empty title returns:

```http
HTTP/1.1 400 Bad Request
```

```text
Task title cannot be empty
```

### Invalid State Transition

Calling `completeTask` for a task whose status is already `DONE` returns:

```http
HTTP/1.1 400 Bad Request
```

```text
Only OPEN tasks can be completed
```

The task remains unchanged.

## Testing

The OData V4 service was tested using the service binding's interactive API tools.

| Scenario | Result |
|---|---|
| Create a task | HTTP 201; generated `TaskId` |
| Create a task | `CreatedAt` populated automatically |
| Create a task with empty `Title` | HTTP 400; validation error |
| Execute `completeTask` for an `OPEN` task | Status changed to `DONE` |
| Execute `completeTask` for a `DONE` task | HTTP 400; business error |
